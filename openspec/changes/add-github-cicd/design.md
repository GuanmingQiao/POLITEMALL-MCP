# Design

## Context

- No `.github/`, no tags, no changelog, no `CLAUDE.md`. History is mostly plain-English commit subjects, not Conventional Commits. `package.json` is `0.1.0`, `private: true`; the only package is `server/control-plane` (Node 22, `tsc`, `node --test`, tests under `tests/`).
- The server is deployed by hand over SSM (`deploy/README.md`). That stays as is in this change.
- The repo is public, so GitHub-hosted runners and Actions are free.
- OpenSpec is used for feature changes (`openspec/`), with archive commits on `main`.

## Goals / Non-Goals

**Goals:**
- Every change is checked by CI before merge; versions are tags created by one automated path.
- Agents get the rules from files they load automatically.
- Leave a clean hook for a later deploy workflow: it can trigger on the `vX.Y.Z` tags and GitHub Releases created here.

**Non-Goals:**
- CD to AWS (OIDC, SSM, health check, rollback) is deferred to a later change.
- No publishing of npm packages or container images to a registry.
- No migration of the OpenSpec history to Conventional Commits; the convention starts now.

## Decisions

1. **release-please over semantic-release, or manual tags + git-cliff.** release-please opens a reviewable Release PR and works with squash merge. Manual tagging is what we want to remove; semantic-release releases on every merge. Config: release type `simple` at the repo root (it also bumps `server/control-plane/package.json` and its lockfile as extra files), `include-component-in-tag: false` (tags look like `v0.2.0`), `bump-minor-pre-major: true` (breaking changes stay minor until 1.0). It runs with a fine-grained PAT stored as `RELEASE_PLEASE_TOKEN`, because PRs and releases created with the default `GITHUB_TOKEN` do not trigger other workflows (CI would never run on the Release PR, and a future deploy workflow would never see the release event).
2. **Squash merge + PR-title lint (`amannn/action-semantic-pull-request`).** Only the PR title needs to be conventional, since it becomes the squash commit. Agents and humans write free-form commits on the branch.
3. **CI shape.** One `ci.yml`: job `test` (checkout, `setup-node` 22 with npm cache keyed on `server/control-plane/package-lock.json`, `npm ci`, `npm run build`, `npm test`), job `docker` (`docker build server/control-plane`, no push), job `openspec` (`openspec validate --all --strict`; exact invocation confirmed during apply). Required status checks: `test`, `docker`, `pr-title`. Workflow `permissions: contents: read`, concurrency cancels superseded PR runs. Actions pinned to SHAs, updated by Dependabot. The Dockerfile uses `npm install`; it moves to `npm ci` so the image and CI use the lockfile identically.
4. **Agent guidance.** Root `CLAUDE.md` is short (commands, layout, pointers) and imports `.claude/rules/cicd.md` with `@`. The rules file holds the flow, conventions and prohibitions, and says AWS deploy is manual. A PR-template checkbox keeps it in sync with workflow changes. `.claude/commands`, `.claude/skills` and `.claude/rules` are committed so teammates and cloud agents get the OpenSpec workflow; they are generated by `openspec init/update`, so regenerate and commit in a `chore:` PR after upgrading OpenSpec rather than hand-editing. `.claude/settings.local.json` is personal and gitignored.
5. **Branch protection is configured by the owner**, documented as a checklist, because it is repository settings, not code.

## Risks / Trade-offs

- **PAT dependency**: `RELEASE_PLEASE_TOKEN` expires and is a secret to rotate → fine-grained, single-repo, contents+PRs write only; if it lapses, release PRs stop updating, nothing else breaks.
- **Squash-only merge hides OpenSpec archive commits' individual messages** → acceptable; archive PRs use `chore:` titles and are hidden from the changelog.
- **Release tags without deploy** → a release does not change the server, so docs must say so clearly (in the agent rules) to avoid the assumption that a tag means "live".
- **`tests/auth/signin-stream.test.ts` drives a real Chromium** (skipped when none is found). Locally on Windows it timed out after ~107 s while the other 309 tests passed. On `ubuntu-latest` it may run against the runner's Chrome → watch the first CI run; if it is flaky, pin `CHROMIUM_PATH` or skip the file in CI with an explicit, documented reason, not silently.
